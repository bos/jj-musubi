# Race condition catalogue

The machines in a hive (one repository replicated by musubi; [design.md,
"Vocabulary"](design.md#vocabulary)) change it concurrently, so every jj-level race that two
processes on one machine can have, machines can have too, plus a few of their own. musubi's rule
is that **replicated concurrency resolves exactly as jj resolves local concurrency**: every
machine ends up with what jj would make of the same operations from concurrent processes on one
machine. Where jj would silently do something harmful only because the operations came from
different machines, musubi detects it and stops.

The tables name the tests that pin each outcome; known limitations without a dedicated test
are marked accordingly. Most tests are in `crates/musubi-sync/tests/races/`, which runs
real repositories, colocated unless the entry says otherwise, through the real protocol core
and hub storage; a few that need the binary are in `crates/musubi/tests/cli.rs`, and a few that
test one layer are beside that layer's other tests. Most tests in `races/` end with
`assert_converged`, which checks that:

- running `jj status` everywhere and syncing again reaches a fixed point within three rounds;
- every machine agrees on visible commits and bookmarks, and shows the working copies of
  every other machine the hive shows;
- in every colocated repository, the git branches match the bookmarks that are neither
  conflicted nor on the root commit;
- a further `jj status` creates no operation.

A few, such as those where replication pauses, check something else instead. The generated
end-to-end tests ([testing.md, "Generated end-to-end
tests"](testing.md#generated-end-to-end-tests)) explore interleavings of the same actions at
random.

## Workspaces

Each machine's workspaces are its own, and every machine shows the others' as workspaces named
after the machine, as `beta/default` ([design.md, "Workspaces"](design.md#workspaces)).

| Race | Outcome | Test |
| --- | --- | --- |
| Each of two machines commits, and they sync | Both commits are visible on both, and each machine has its own workspace and shows the other's under the machine's name, as `beta/beta`. | `basic_replication_converges` |
| Two machines both use workspace `default` | Fine: each keeps its own `default@`, and shows the other's as `alpha/default@` or `beta/default@`. | `machines_may_share_a_workspace_name` |
| A machine forgets another machine's workspace | Local only: nothing changes elsewhere, not even an empty working-copy commit, which `jj workspace forget` would otherwise abandon. The next sync shows the workspace again, even if the other machine has done nothing since. So too when the forget merges with a line of history from before that working copy existed, or before that machine joined. | `other_machines_workspaces_are_theirs`, `other_machines_workspaces_are_theirs_through_a_merge` |
| …while that machine builds on its working-copy commit | Nothing moves. `jj workspace forget` abandons the empty commit on the forgetting machine, but the hive keeps it, and the forgetting machine shows the workspace again as its next sync starts, before it merges what the other machine built. A forget made while a sync is under way merges as on one machine, the other machine's work rebased off the commit. | `forgetting_another_machines_workspace_moves_nothing_built_on_it` |
| A machine forgets another machine's workspace, then rewrites or abandons the parent of its empty `@` | jj, no longer seeing that `@`, leaves it on the old parent. musubi lets it go rather than bring the old parent back as a divergent copy, and the other machine gets a fresh `@` where jj would have moved it: on the rewritten parent, or on the abandoned parent's own parent. Since a rewrite keeps the change id, a parent moved with `jj rebase -r` counts as rewritten, as it does when jj merges concurrent operations, though a local `jj rebase -r` would have left the working copy behind. | `forgotten_working_copies_dont_keep_rewritten_parents`, `forgotten_working_copies_follow_an_abandon_to_the_parent`, `forgotten_working_copies_follow_a_parent_rebased_by_an_abandon`, `forgotten_working_copies_follow_a_moved_parent` |
| A machine forgets another machine's workspace, then, before syncing, abandons its `@`, which the forget left visible: it has edits, or another commit is built on it | As it would had the workspace still been there: the abandon stands, and the other machine gets a fresh `@` on the parent. musubi keeps a forgotten `@` visible only where the forget abandoned it. | `forgotten_working_copies_can_be_abandoned`, `forgotten_working_copies_built_on_can_be_abandoned` |
| A machine adds, then forgets, a secondary workspace | Every machine shows it while it exists. | `secondary_workspaces_show_everywhere` |
| A machine rewrites the parent of another machine's `@` | jj moves that machine's workspace at once, as it moves any workspace's, and that machine follows. jj then treats its working copy as stale until `jj workspace update-stale` updates the files, or, with `snapshot.auto-update-stale = true`, its next command does. | `rewriting_under_another_machines_working_copy_is_allowed`, `other_machines_working_copies_follow_rewrites` |
| …while that machine has unsnapshotted edits | The edits survive: jj snapshots them at the old operation before updating. At worst the working-copy change diverges. | `unsnapshotted_edit_survives_a_remote_rebase` |
| A machine abandons another machine's working-copy commit | jj gives that workspace a new commit on the parent, as for any workspace, and its machine adopts it. | `abandoning_another_machines_working_copy_commit` |
| A machine renames its workspace | The other machines show the new name. | `renamed_workspace_shows_renamed` |
| A machine renames or forgets its workspace while another machine rewrites its working copy | The rename or forget wins, as when jj merges concurrent operations on one machine: musubi merges workspaces three-way as jj does, removals first. | `e2e_smoke`, `workspace_merge_matches_jj` |
| Several machines share a hostname | Told apart by a random suffix in each machine's stored identity, and shown as `mac-1a2b/default`. | `machines_sharing_a_hostname_are_told_apart`, `two_machines_sharing_a_hostname_show_each_other_qualified` |
| A workspace name git can't store as a ref, an import in a repository that isn't colocated, or a git remote named after a machine | Nothing happens: other machines' working copies are never git refs, so git can't drop them, and jj's import never abandons work because of them. | `git_never_sees_other_machines_working_copies` |

## Copies that go away

`musubi forget` forgets another machine's *copy* ([design.md,
"Vocabulary"](design.md#vocabulary)), and `musubi leave` this machine's own: the hive stops
showing the copy's workspaces. A forget removes only the copy's work it saw, and only the copy's
own work brings it back ([design.md, "Copies that go away"](design.md#copies-that-go-away)).

| Race | Outcome | Test |
| --- | --- | --- |
| A machine forgets another machine's copy | Every machine stops showing its working copies; its empty working-copy commit is abandoned, and its work stays. The forgotten copy keeps its working copy, on the hidden commit, with no new one for the others to see, and stays forgotten however often its daemon syncs, until its next work. | `a_forgotten_copy_comes_back_with_its_next_work` |
| …and the forgotten copy's next work leaves its working copy alone, as creating a bookmark does | It shows again with a new working-copy commit on the old one's parent, as jj gives a workspace whose commit is abandoned: the forget abandoned its empty one. | `a_forgotten_copy_back_by_other_work_gets_a_new_working_copy` |
| …and the forgotten copy realizes the forget together with the operation before it | It keeps its working copy, as its realization of that operation had it. | `a_forgotten_copy_keeps_its_working_copy_through_a_run` |
| …and the forget, which saw the copy add a workspace, merges with work from before it | The copy keeps its workspaces as its latest work left them, whichever parent the merge lists first. | `a_forgotten_copy_keeps_its_latest_workspaces_through_a_merge` |
| A machine forgets a copy that is working meanwhile | The work the forget didn't see keeps the copy. | `work_a_forget_didnt_see_keeps_the_copy` |
| …having rewritten the copy's working-copy commit before forgetting it | The merge keeps the old commit hidden, beside its rewrite, and the copy, present by its work, follows the rewrite. | `a_rewrite_before_a_forget_sticks_through_a_merge` |
| A copy leaves while another machine pushes | It merges its forget with the push, and stays gone. Its working-copy commit, which has changes, stays as an ordinary commit, and it keeps its working copy. | `leaving_sticks_through_a_merge` |
| Two machines forget the same copy at once | They agree. A forget of a copy already gone writes nothing. | `concurrent_forgets_agree` |
| A machine undoes its forget of another copy, or restores a view from before it | The forget stands: only the copy's own work brings it back. The copy's workspaces come back in that machine's view, under names the hive no longer gives them, and it takes them for no machine's, its own included, and drops them as it syncs. | `undoing_a_forget_brings_back_nothing` |
| A machine's own workspace is named with a `/`, as `feat/x` | It stays here, but no other machine shows it: names of that form are kept for other machines' workspaces, and `musubi status` says so, with the command that renames it. Renamed without the `/`, it shows everywhere. | `own_workspaces_with_a_slash_stay_here_until_renamed` |
| …and named like another machine's, as `beta/x`, before that machine joins or after | It stays here, apart from that machine's, while the hive has forgotten this machine too, and after `jj undo` of forgetting it; it shows that machine as `beta-1a2b`. This machine has a working copy for it, which no other machine's workspace has here. | `own_workspaces_named_like_another_machine_stay_apart` |
| …and named like the workspace of a copy the hive has forgotten, as `beta/beta`, which then comes back with work | It stays here, and the returning copy doesn't show it, as `alpha/beta/beta`: this machine shows the returning copy's own workspace under its longer name, as `beta-1a2b/beta`. | `a_local_name_like_a_forgotten_copys_workspace_stays_local_when_it_returns` |
| …and that machine, in an operation of its own, forgets the workspace it runs in | This machine records the operation as made in `beta-1a2b/default`, the name that machine's workspaces show by, so that `jj undo` in a workspace of its own named `beta/default` doesn't take the operation for its own. | `an_operation_that_forgot_its_workspace_keeps_its_name` |
| …and named like another machine's, added while that machine adds its workspace `x`, or joins with one, before this machine syncs | It stays here, and neither working copy moves, then or through `jj undo` of forgetting it. Realizing that machine's work, this machine shows it clear of the names in its op heads that it has working copies for, as `beta-1a2b/x`, and names it so at the merge of the two. A realization made before the `jj` command that adds the workspace, and not yet published, as across a crash, is realized again first. Realized as `beta/x`, that machine's workspace took the place of this machine's in jj's merge, and this machine's snapshots moved that machine's working copy. | `own_workspaces_named_like_one_added_meanwhile_stay_apart`, `own_workspaces_named_like_one_of_a_machine_joining_meanwhile_stay_apart` |
| …and named like another machine's, added, or renamed to, after `jj workspace forget beta/x` here | It stays here: forgetting another machine's workspace stays local, and the next sync shows that one as `beta-1a2b/x`, where that machine has it. A `jj` command that adds a name none of the views it started from had moves nothing of that machine's, and no later command does either: this machine has a working copy for the name. Realizing that machine's concurrent work, as where it moves its `x`, this machine keeps `beta/x` as the base of their merge has it, since the merge takes dropping the name for a removal, which wins over this machine's workspace. | `own_workspaces_named_like_one_forgotten_here_stay_apart` |
| …and named like another machine's, added by a `jj` command that publishes during the sync step that merges that machine's work adding `x`, after the step read the op heads, or while a sync shows that machine's `beta/x` again after `jj workspace forget beta/x` | A known limitation. Both are `beta/x` in this machine's view, and jj's merge keeps one working copy under the name. Where it keeps that machine's, the two workspaces share its commit, and a snapshot in this machine's moves that machine's working copy. A name without a `/` avoids it. | — |
| …and named like another machine's workspace that the hive shows by that name, then renamed or removed (`jj workspace rename`, `jj workspace remove`) before musubi canonicalizes the commands run in it, or canonicalizes them again after losing its translation cache; or forgotten (`jj workspace forget`) before that machine's workspace arrives under the name | A known limitation. A `/` name is never this machine's own to publish, but whether such a workspace here is an unpublished one of this machine's, or another machine's shown under that name, comes from jj's workspace store as it is now, not as it was when a command ran, and `jj workspace forget` leaves the name there. In the first case the commands' names stand for the other machine's workspace, which moves to this machine's commit; in the second this machine takes the other machine's workspace for an unpublished one of its own, shows it under both names, and `musubi status` warns about it. A name without a `/` avoids both. | — |
| …and named like another machine's, which this machine shows again under a longer name, as `beta-1a2b/x` after `jj workspace forget beta/x` and adding its own, while that machine moves it, before the operation that shows it again reaches the hub | A known limitation. jj merges the two in order of their end times and keeps the first, which shows the workspace where it was: it goes back there, and jj treats that machine's working copy as stale. After a `jj commit` there, it goes back to the commit it committed. | `a_workspace_shown_again_by_a_longer_name_can_lose_a_move_meanwhile` |
| A copy removes its last workspace | It remains present and can be named for `musubi forget`, including by a qualified name when local workspace names reserve its plain prefix. | `a_copy_without_workspaces_can_be_forgotten_by_name` |
| A copy leaves, its empty working-copy commit abandoned by its forget, or leaves after another machine forgot it | It gets a new working-copy commit, as jj gives a workspace whose commit is abandoned: no next work of its shows it again. | `a_copy_that_leaves_gets_a_new_working_copy` |
| A copy is unused for longer than its `musubi.forget-after` | Any other machine's daemon forgets it, as `musubi forget` would, and it comes back with its next work, as above. A copy that recorded none, or `never`, isn't forgotten, nor is a machine's own copy by its own daemon. | `unused_copies_are_forgotten_after_their_forget_after` |
| A forgotten copy changes its `musubi.forget-after` | Recording it is the copy's work, so the copy shows again, and is forgotten by the new value. | `changing_forget_after_is_work` |
| A copy that left joins again | It shows again at once: joining is its work. | `a_copy_that_left_shows_again_once_it_joins` |
| A machine rewrites the working-copy commit of a copy the hive has forgotten | No machine sees it as a working copy, so no workspace moves with it; the copy follows the rewrite itself, as jj would have moved it. | `a_forgotten_working_copy_follows_its_rewrite` |
| A machine rewrites or abandons the parent of a forgotten copy's working-copy commit, hidden, as is the empty one a forget abandons | No machine sees the commit as a working copy, so jj leaves it on the old parent, and the copy's next snapshot would bring that back on every machine: beside its rewrite, divergent, or abandoned no longer. So the copy rebases the commit itself, still hidden, in an operation that isn't its work, as jj rebases a working copy when it merges concurrent operations: onto the parent's rewrite, found by its change id, or onto an abandoned parent's own parents. A parent rewritten divergently says nowhere to go, so it counts as abandoned. If that changes the copy's files, its working copy is stale, as is any workspace jj moves: jj, updating it, snapshots unsnapshotted edits into a commit beside the working copy, and takes them off the disk until the copy's next sync follows that commit and its next command updates the files again. | `a_forgotten_working_copy_follows_a_rewrite_of_its_parent`, `a_forgotten_working_copy_follows_an_abandon_of_its_parent` |
| …while a `jj` command in the copy snapshots in the instant between a sync showing it the rewrite and rebasing its working copy | A known limitation: the snapshot brings the old parent back, as before. | — |

## Bookmarks and tags

| Race | Outcome | Test |
| --- | --- | --- |
| An ordinary jj command follows a native operation merge that selects a new bookmark, while Git still matches the merged import record | jj exports the selected bookmark even though importing changes nothing. | `an_unchanged_import_exports_a_bookmark_selected_by_a_merge` |
| A machine's node merges its own concurrent work with an operation from the hub, and jj's merge moves a bookmark | The merge is the machine's op head, so its `.git` shows the moved branch, as for any other operation musubi publishes as an op head. | `bookmark_moved_by_a_node_merge_is_exported` |
| Same bookmark moved to different commits | Conflicted bookmark on every machine. Each colocated `.git` keeps its own branch value, because jj does not export conflicted bookmarks. No later `jj` command resolves it silently. Resolving it on one machine resolves it everywhere and updates every `.git`. | `same_bookmark_moved_to_different_commits` |
| Same bookmark created at the same commit | No conflict. | `same_bookmark_created_at_the_same_commit` |
| Same bookmark deleted on both machines | Deleted; no conflict. | `same_bookmark_deleted_on_both_machines` |
| Bookmark moved on one machine, deleted on another | jj's three-way result, the same on every machine. | `bookmark_moved_on_one_machine_and_deleted_on_another` |
| Branch moved with `git` behind jj's back while another machine moves the bookmark | The git move is imported by that machine's next `jj` command, as a local change; the hive converges, with no flip-flopping. | `git_branch_moved_behind_jj_while_another_machine_moves_it` |
| Same tag set to different commits | Conflicted tag on every machine. Each machine's `@git` tag keeps its own value. | `same_tag_created_at_different_commits` |
| One machine fetches an annotated tag | A known limitation: every machine's jj has the tag, at the same commit, but only that machine's `.git` has the tag object, with its message, tagger and any signature. The others' `.git` has a lightweight tag at the commit, so there `git describe` without `--tags` passes it over, and `git tag -v` has nothing to verify. jj records a tag by its commit, and musubi moves the commits a view needs, not tag objects. | `an_annotated_tag_arrives_lightweight` |
| Independent repositories with differing `main` join one hive | The histories merge at jj's shared root operation, and `main` is conflicted until someone resolves it. | `joining_repositories_with_conflicting_bookmarks` |
| A joining copy and the hive have fetched different points on one forward history | jj takes the descendant from either copy. Neither machine has priority. | `joining_takes_the_newer_main_from_either_copy` |
| A joining copy and the hive observed different rewrites of upstream history | The command attempts a native fetch and syncs its effects, preserving local work and checkout files. An unavailable remote leaves a warning and the conflict; rejoining retries. A fresh fetch can select a target neither copy knew. | `joining_fetches_ambiguous_remote_bookmarks`, `e2e_join_after_upstream_rewrite` |

## Changes

| Race | Outcome | Test |
| --- | --- | --- |
| Same commit rewritten on two machines | A genuine divergent change, identical, with the same commit ids, on every machine. Any machine's `@` built on that commit is rebased by both rewrites and diverges too, as with two workspaces on one machine. Resolving the divergence anywhere resolves it everywhere. | `same_change_rewritten_on_two_machines` |
| Commit abandoned on one machine while another builds on it | The orphan is rebased onto the abandoned commit's parent exactly once, so nothing diverges. | `commit_abandoned_while_another_machine_builds_on_it` |
| Both machines squash different work into the same commit | A divergent change, the same everywhere. | `both_machines_squash_into_the_same_commit` |
| A conflicted commit made on one machine | Conflicted, with the same terms, on every machine; resolving it anywhere resolves it everywhere. | `conflicts_replicate_and_resolve` |
| A child of the root is abandoned while another machine makes it a merge parent | jj drops the root parent when rebasing the merge, and the hive converges. | `abandoning_a_root_child_beside_a_merge_converges` |
| Three machines build on, and one rewrites, the same commit | Merged one at a time through the hub; no spurious divergence. Independent merges on each machine would each rebase the same commits and create divergence, which is why the hub orders updates ([design.md, "Ordering: one hub, one canonical head"](design.md#ordering-one-hub-one-canonical-head)). | `three_machines_build_on_the_same_commit` |
| One machine rewrites a commit another builds on, with commit signing on | The commits musubi rebases when it merges the two are signed, as jj's own rewrites would be: musubi loads jj's signing config as jj does. | `rewrites_are_signed_as_jj_signs_them` |

| A machine changes Git remote definitions while another copy syncs, with a config lock held or after reopening | Definitions stay local and byte-for-byte unchanged by sync. Receiving remote bookmarks never creates a remote. | `remote_configuration_stays_local` |

## Kinds of repository

These cases check backend and object-transfer behavior alongside the races.

| Kind | Outcome | Test |
| --- | --- | --- |
| A machine's repository isn't colocated | Fine: its git store is inside `.jj`, or elsewhere outside its workspaces, where musubi reads and writes objects, with no `.git` to keep in step. Its work and bookmarks reach colocated machines, whose `.git` gets the branches, theirs reach it, and it merges concurrent work like any other machine. | `colocated_and_non_colocated_repositories_share_a_hive` |
| History has a submodule | Fine: trees name the submodule's commit, which no machine needs, and nothing transfers it or asks for it. | `history_with_a_submodule_replicates` |
| A shallow or partial clone | Refused, at once, with a pointer to `musubi clone`: starting a hive, joining one, and syncing a repository that has become one since it joined. Neither can send everything an operation requires, which the hub accepts only whole. musubi's git also sets `GIT_NO_LAZY_FETCH`, so a git that knows it never fetches from a promisor remote. | `shallow_clones_are_refused`, `shallow_and_partial_clones_are_incomplete` |

## Operation history

Independent merges can share a canonical id when their frontier and operation metadata match.
`independent_merges_can_reuse_a_canonical_operation` fixes the metadata on two copies, then
checks the first write's new raw vertex and the second write's reuse against the structural
write model. Another receiver realizes that merge before rollback, then recreates it without
adding a label. The same case leaves an ancestor beside the merge through the shipping
head-store update, then checks that the core removes the ancestor without writing a canonical
operation. The search does not force identical operation metadata on different copies.

`interrupted_git_export_can_leave_aliased_operation_heads` covers a separate physical case:
an interrupted replacement by a Git-exported copy leaves two physical operations with the
same canonical id. The next merge writes a new canonical child of that id. The search does
not interrupt Git export's physical head replacement.

| Race | Outcome | Test |
| --- | --- | --- |
| The hub is made again between requests while a machine has received operation metadata but lacks its objects | An empty object reply ends the round instead of repeating the same request. The retry fetches the new hub's head and finishes before another machine republishes the old data. | `an_empty_object_reply_retries_from_the_remade_hub` |
| `jj undo` when the latest operation came from another machine, even with both workspaces named `default` | jj refuses, naming the other machine's workspace (`alpha/default`), since musubi realizes other machines' operations under those workspaces' names. With `--allow-cross-workspace` the undo happens and replicates. To undo this machine's own earlier operation once others have arrived, use `jj op revert <op>`. | `undo_of_another_machines_operation`, `op_log_names_other_machines_workspaces` |

## Known jj limitations

These are jj 0.47 behaviors, reproducible on one machine with concurrent `jj` processes or
`--at-op`. musubi doesn't cause them, but more concurrency makes them likelier.

When a test or the search finds a jj bug, report it in three steps:

1. File a tracking issue in jj-musubi, labeled `jj` and titled for what jj should do
   ("jj: …"). Say what goes wrong, what musubi does about it, and what to change here once
   jj is fixed.
2. File a succinct issue against [jj](https://github.com/jj-vcs/jj/issues), with a minimal
   reproduction in plain jj, checked against jj's main branch.
3. Comment on the tracking issue with a link to the jj issue, saying it has been filed.

| Behavior | Effect | Recovery | Test |
| --- | --- | --- | --- |
| A foreground jj process holds a non-colocated workspace's working-copy lock while musubi starts a background snapshot | jj's mutation API waits for the lock. If the holder stalls, stopping or restarting the daemon waits for the scan to finish. | Let the foreground command finish or stop it. | — |
| Concurrent operations whose rebases form a loop: one moves X, and Y on it, onto Z, while another moves Z onto Y | jj panics merging them ("graph has cycle"), and so on every load: every `jj` command crashes. musubi doesn't apply another machine's operation that jj can't merge with this machine's own, as above, so across machines jj keeps working; two operations on one machine still break it. The sync error names the operation to revert: the newest of this machine's operations the hive doesn't have whose revert, tried as `jj op revert` would make it, lets jj merge the other machine's operation (newest, since reverting an operation whose result was rewritten since leaves a divergent change, which can untie the loop too). Where no single revert will do, as when several operations each loop with it, it names the first whose own change, from its parent, jj panics merging with the other machine's operation, skipping operations already reverted; the next sync names the next. Where it finds neither, the error lists them as above. | Revert the operation the sync error names with `jj op revert <id>`, on top of everything since: jj rebases later work off what it rewrote (a change rewritten again since is left divergent), and musubi catches up. | A command at an older operation (`--at-op`), such as `jj new`, in a colocated workspace where that operation has no record of git's HEAD, as for a workspace renamed since | The command still sets git's HEAD, to its new working copy's parent. ## Protocol-level races

Lost, duplicated, reordered and delayed messages; concurrent pushes, where one wins and the others
merge and retry; node and hub crashes at every step; rogue pushes without uploads. The Lean
model's proofs cover these for any number of nodes, and `protocol_invariants` and `conformance`
check the Rust core against it ([testing.md, "Protocol property
tests"](testing.md#protocol-property-tests)).
